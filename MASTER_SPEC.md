# Claims platform — master spec sheet

**Status:** Business rules P1–P24 and API contract decisions C1–C6 are **approved with the C5/C6 corrections below**. Section 8 describes focused acceptance scenarios, not executable tests. No application or test code is implied by this document.

**Sources:** `V2_BackEnd_candidate_assessment_brief.docx` and the earlier workflow and architecture discussion. The brief describes six APAC markets but does not identify them or prescribe statuses, policy rules, or targets.

**Reading key:** **Agreed**, **Approved [P#]** and **Approved [C#]** identify confirmed requirements. P IDs track business decisions; C IDs track the approved HTTP contract and test-fixture choices. The revisions to P2, P11, P15 and P23 remain approved.

## 1. Scope and boundaries

- **Agreed:** One locally runnable Java/Spring Boot application, PostgreSQL as the source of truth, and a small same-origin frontend to use and demonstrate the backend. Refreshing the page reads persisted changes; push/live browser updates are not required. The backend, not the frontend, enforces every permission and transition.
- **Agreed:** Exactly two login roles: **claimant** and **claims officer**. Accounts are pre-created with email and securely hashed passwords; no public registration, verification email, or OAuth. Claimants report motor/property incidents and track, answer requests, and receive decisions. Officers work within their team, assess, decide, release, confirm payment, and view team workload and exposure. No manager role.
- **Agreed:** One claims application owns claim state, assignment, requests, decisions, payment confirmation, and reported-claim exposure. REST/HTTP and PostgreSQL handle all claim actions and authoritative reads. Kafka delivers asynchronous **in-app dashboard notifications** when information is requested, a claimant answers, or a decision is made; it never controls claim state, assignment, payment, or exposure. PostgreSQL commits state and history together. No file upload, payment transfer, automated policy verification, or frontend live update.
- **Agreed:** A claim action must succeed if PostgreSQL can commit even when Kafka is unavailable; its notification is delivered later after Kafka recovers. Retries must not produce duplicate dashboard notices.
- **Approved [P1]:** The application represents only reported claims entered here; no imported phone/email claims, outbound email/SMS/push notifications, document storage, payment integration, refunds, partial payments, reopening, or real insurance reserving ledger in this scope. In-app Kafka-backed dashboard notifications **are** in scope. *Reason:* distinguishes the requested in-app delivery from external communications and financial guarantees.
- **Agreed:** A typed policy reference does not verify policy existence, ownership, eligibility, or Chubb coverage. The officer records a coverage assessment and explanation; claimant-supplied amounts and estimates are not automatically payable amounts.
- **Agreed:** A claimant can report an incident without knowing the policy reference or requested loss amount. Missing values stay **not provided** (null), never a fabricated reference or zero; the report still receives a claim reference and enters the team queue.

### Architectural decision against the brief

One Spring Boot application keeps ownership, lifecycle checks, activity writes, and exposure interpretation in one PostgreSQL transactional boundary. REST handles reporting, reads, pickup, release, requests, answers, assessment, decisions, mark-paid, and notification-list reads: callers need authoritative responses. On-demand PostgreSQL queries, indexed and paginated for lists, suit write-on-action/read-often queues without an early cache or read replica for **claims**. Kafka carries committed notification events to a separate asynchronous notification handler within this application, which stores a dashboard notification read model in PostgreSQL. The browser reads that model over REST on refresh; it does not connect to Kafka. This is a real broker-backed delivery path with its own lag and recovery behavior, not a second source of truth for claims. REST claim responses do not wait for a Kafka acknowledgment or for notification consumption.

## 2. Data and ownership model

Logical schema (column names illustrative; FK/uniqueness and invariants are required):

| Data | Identity, relationships, and important attributes |
| --- | --- |
| `accounts` | Unique ID and normalized unique email; password hash; exactly one role; active/disabled status; claimant market affiliation or officer team membership as appropriate. No password hash in API responses or history. |
| `teams` | ID, display name, routing/market scope; officers belong to a team and claims have an explicitly stored `team_id`. |
| `markets` / routing configuration | Market code, allowed currency, and mapping from market and claim type to responsible team; configured locally, not claimant-controlled. |
| `claims` | ID and stable public reference; claimant ID (exactly one), team ID (exactly one), nullable assigned officer ID (at most one); market, currency, MOTOR/PROPERTY, incident date/location/description and affected asset; nullable policy reference and nullable requested amount; status; next actor; coverage conclusion/reason, nullable assessed loss and nullable pre-decision estimated unpaid amount; nullable decision type/reason, settlement amount, decision time; nullable paid time/paid-by; version; current-assignment substantive-action flag; created/updated timestamps. |
| `information_requests` | ID, claim ID, requesting officer, question, created time; OPEN, ANSWERED, or WITHDRAWN; optional claimant answer/answered time or withdrawal reason/time/actor. Retain completed requests. |
| `claim_activity` | Append-only claim ID, event kind, actor account ID/role, timestamp and safe details: report, pickup, request, answer, withdrawal, assessment, release (including reason when supplied), decision, and mark-paid. Separate internal details from claimant-facing progress. |
| `idempotency_records` | Unique `(actor_id, operation, client_key)`; request fingerprint and stored original outcome/reference and response snapshot, committed atomically with the corresponding claim action. |
| `notification_outbox` | Unique event ID, source claim/activity ID and version, REQUESTED/ANSWERED/DECIDED type, destination ACCOUNT or TEAM and its ID, occurred time, minimal display-safe metadata, retry/publish metadata, and nullable delivered time. | `dashboard_notifications` | Unique event ID, destination ACCOUNT or TEAM and ID, claim ID, type, occurred/delivered times and safe reference data. Materialized by the Kafka consumer in PostgreSQL, never by the claim write path. Unique event identity prevents duplicate notices on redelivery. |

- **Agreed:** `team_id` is explicit; assigned officer is either null or an officer authorized for that claim's team. An owned claim is read-only to other officers in that team. Claimant ownership is by authenticated account ID, never by an email, claim ID, or claimant ID supplied in a write payload.
- **Approved [P2]:** Each pre-created claimant account is affiliated with **one** configured market and can report incidents **only in that own market**; there is no market picker for reporting on someone else's market. The authenticated session and report form display that market's code/name and currency before submission; the report confirmation and claimant's own claim list/detail show the saved market and currency afterward. The backend derives market from the account, currency from market configuration, and team from market + claim type routing; it rejects a client-supplied conflicting market, currency, or team instead of trusting the browser. Officers have one team. Reject unknown routes. Market, currency, claimant, and team do not change after reporting; cross-market claims and reassignment between teams are outside scope. **Seed only market SG, currency SGD and one team routing both MOTOR and PROPERTY**; provide pre-created accounts affiliated accordingly. Keep the market/currency and market/type→team mappings configurable in data/configuration, with **no SGD-specific logic**. Other currency/market entries may be supplied by later test fixtures, not production seed data; the other five markets in the brief are not represented by invented Chubb assignments. *Reason:* a small honest local seed that still exercises configurable routing and currency-safe aggregation.
- **Approved [P3]:** Amounts **when provided** are nonnegative fixed-precision decimal values, stored with explicit ISO currency; no floating-point calculations or exchange-rate conversion. Required report fields are type, occurrence date, location, narrative, and affected asset. Policy reference and requested loss amount are optional and nullable; an absent amount is **unknown**, not zero, and an absent policy reference is **not provided**, not evidence that no policy exists. A supplied reference remains unverified. Text fields have bounded length; timestamps are instants stored in UTC and presented in an appropriate local context. *Reason:* reporting should not require estimates or paperwork the claimant lacks, while any values eventually supplied remain meaningful.
- **Approved [P20]:** An officer can request a missing policy reference or loss amount using the existing information-request workflow. The claimant's answer is retained as text on that claim; it may also include optional structured `policy_reference` and/or `requested_amount` fields to fill or correct those claim fields. Omitted structured fields leave stored values unchanged; only explicitly supplied validated values update them, with the change attributed to the claimant in history and claim version advanced. An answer consisting only of text does **not** silently parse text into a policy reference or amount; those fields remain not provided until explicitly supplied. There is no new claim, no forced request merely because either value is absent, and no automatic conversion of a requested amount into assessed loss or exposure. *Reason:* missing information can be supplied later without guessing from prose or blocking first notice of loss.
- **Approved [P4]:** `coverage_conclusion` is UNKNOWN, APPEARS_COVERED, or APPEARS_NOT_COVERED, with an officer-authored reason for a recorded conclusion. An officer can revise assessment (with history) while undecided; assessed loss and pre-decision estimated unpaid amount are independently nullable and editable, not computed from requested amount. An estimate of **0** must be explicitly entered to mean known zero; null means unknown. *Reason:* evidence, apparent coverage, and expected insurer cost answer different questions; no real policy engine exists.
- **Approved [P5]:** Use database FKs, a unique public reference and normalized account email, an index for team/status/assignee/created time and claimant/created time, plus a constraint/index allowing at most one OPEN information request per claim. List and dashboard reads are server-filtered and paginated where lists can grow; claim/exposure aggregates are computed from committed PostgreSQL claim state rather than asynchronous projections. Notification lists read their separate Kafka-fed PostgreSQL projection [P21–P24]. *Reason:* predictable authoritative queues and measures without confusing notification lag with claim state.

## 3. Identity, authorization, and visible information

- **Agreed:** Only logged-in claimants see their own claims, their requests and answers, meaningful progress, and their decisions. Officers see the incoming and team lists for their own team; a claim owned by another officer is readable, never mutable by them. Ownership does not confer another team's access. The frontend is not an authorization boundary.
- **Approved [P6]:** Use Spring Security server-side sessions with secure password hashing (e.g., BCrypt or Argon2), HttpOnly cookies, secure-cookie settings when served over HTTPS, session fixation protection, and CSRF protection on state-changing same-origin requests. Seed accounts without committing usable secrets. Unauthenticated requests get 401; wrong role or a visible-but-nonowner mutation gets 403; a record outside the caller's authorized visibility is indistinguishable from a missing record (404). Login/logout are explicit operations. *Reason:* same-origin browser authentication without bearer tokens or public registration; the local HTTP setup must document its cookie limitations.
- **Approved [P7]:** Claimants see their own claim's saved market/currency, any policy reference or requested amount they provided (otherwise **not provided**), request text, submitted answer, high-level status/next actor, settlement amount or rejection explanation, and whether a settlement is marked paid. They do **not** see internal coverage reasoning, estimated exposure, release reasons, officer notes, other accounts, or team financial totals. Officers in the team see full claim activity, including historical release reasons, but not password data. A claimant-facing progress feed is a safe projection of history, not the raw officer activity log. Delayed notices link back to these authoritative role-scoped views; they do not carry raw request/answer text or decision reasoning through Kafka [P21]. *Reason:* transparency without leaking internal or cross-claim information.

## 4. Lifecycle and invariants

**Agreed progression:** `REPORTED` → `UNDER_REVIEW` ↔ `WAITING_FOR_CLAIMANT` → `SETTLED` or `REJECTED`. Settlement begins unpaid; marking paid confirms an externally completed payment, does not initiate one, records actor/time, and cannot create a second confirmation. Requested, assessed, estimated unpaid, and settled amounts are distinct.

- **Approved [P8]:** `REPORTED` means reported and awaiting first pickup. Pickup changes `REPORTED` to `UNDER_REVIEW`; otherwise it preserves the existing status, including `WAITING_FOR_CLAIMANT` and settled-but-unpaid `SETTLED`. Release never resets a claim to `REPORTED`: an unassigned `UNDER_REVIEW` claim's next actor is an officer, an unassigned `WAITING_FOR_CLAIMANT` claim's next actor is the claimant, and an unpaid `SETTLED` claim's next actor is an officer for payment confirmation. Answering an open request returns it to `UNDER_REVIEW` with next actor officer whether or not an officer is assigned. Claim status and `next_actor` are both exposed in permitted views so status alone never promises active ownership. *Reason:* handoffs preserve progress and payment state.
- **Agreed:** Atomic pickup works only on a claim with no assigned officer in the caller's team; two concurrent officers cannot both own it. No direct taking of an owned claim. The owner may release it; every release is logged, including optional/required typed reason. Release retains claim, history, and outstanding requests.
- **Agreed:** A typed nonblank release reason is mandatory only when that owner has performed a first substantive action **since their current pickup**; pickup itself is not substantive. Maintain an explicit `substantive_action_since_pickup` flag rather than deriving the requirement from history; reset on each pickup, set in the same transaction as the substantive act, and check atomically on release. A prior officer's actions do not force the next officer to give a reason before that next officer acts.
- **Approved [P9]:** Creating or changing a coverage/loss/exposure assessment and creating an information request count as substantive actions; viewing, pickup, claimant answers, and release do not. Once true, the current-assignment flag stays true even if an assessment is revised or a request withdrawn; only the next pickup resets it. Decision itself is substantive but normally ends decision-making; if settled-unpaid release is allowed, a decision also makes its release reason mandatory. A release after an unanswered request leaves the request OPEN. A claimant answer can close that request while unassigned and returns the case to the same team's unassigned review queue, never to the previous owner. *Reason:* defines the flag's exact triggers and avoids losing an answer during a handoff.
- **Approved [P10]:** At most one OPEN information request per claim. Only the owning officer may create or withdraw it; only the claim's claimant may answer it with nonblank text, exactly once. An answer is immutable; follow-up requires another request. The owning officer may withdraw an OPEN request with a nonblank reason; withdrawal closes the request but does not fabricate an answer. Neither terminal decision may commit while a request is OPEN. A request remains answerable after release, before another officer picks up. *Reason:* clear add-information semantics and no decision that silently ignores a promised answer.
- **Approved [P11]:** Only the owning officer may decide. **Before settlement**, the officer must have recorded a non-null, nonnegative **assessed loss** and an `APPEARS_COVERED` coverage assessment **with a reason**; settlement also requires a positive amount and an explanation. A missing requested amount or policy reference does not by itself prevent settlement. Rejection requires a nonblank reason **but not assessed loss**; it also does not require a negative coverage conclusion (there may be other reasons). No automated rule claims that settlement must equal or be bounded by the requested amount or assessed loss. Decision is final for adjudication: no second decision, editing, or reopening in this scope. *Reason:* an officer must record the assessed loss and apparent coverage before offering a settlement without pretending the policy reference was verified.
- **Approved [P12]:** A settlement retains status `SETTLED` and a separate unpaid/paid indicator. Only its assigned owner may mark it paid, once, with confirmation actor/time and an activity entry. An unpaid settled claim may be released (with the conditional reason), picked up by another team officer, and paid by that new owner; a rejected or already paid claim cannot be released or picked up. A repeat by the same current owner returns the original paid confirmation without writing another activity entry [P15]. *Reason:* handoff must not strand confirmation of an external payment; payment is distinct from decision and does not transfer funds.

## 5. Retries, concurrency, and observable failures

- **Approved [P13]:** Claim reporting, information-request creation, claimant answer, and either final decision require a client-generated idempotency key. Scope uniqueness by authenticated actor and operation; a stored fingerprint of the substantive request prevents reuse of the key with different content (conflict). Store the original stable response snapshot, not merely the current claim, in the same transaction as state/history and (for notice-producing actions) **one** outbox row. A concurrent identical retry waits for, or observes, the committed original and receives the same result/reference with no duplicate claim action, activity, or outbox event; a failed transaction leaves no success record. The same actor must still be authenticated and allowed to **view** the original claim on replay; no new ownership/transition check is applied to the already-committed action (so a former owner can retrieve their original result after release). A different key is a new attempt: a second report may be a genuine second incident and is not deduplicated by resemblance, whereas a second decision conflicts with the terminal state; a genuinely new request after an earlier request was answered is distinct work, not a retry. Key retention is durable for the local application rather than silently expiring during normal use. *Reason:* lost HTTP responses must not duplicate claims, outcomes, or notifications; fingerprint and response storage make replays meaningful.
- **Approved [P14]:** Serialize mutations of the same claim using a PostgreSQL transaction and row lock or equivalent compare-and-set/version check; state, requests, exposure-affecting fields, idempotency result, and history commit or roll back together. Decision requests include the version the officer last reviewed; claimant answers, request withdrawal, and substantive assessment edits advance it (as do other claim mutations that could invalidate an officer's view). If an answer commits before a stale decision, decision returns conflict and the officer must reread; if a valid decision commits first, no later answer to a closed/withdrawn request is accepted. A decision may not bypass an OPEN request: the officer must explicitly withdraw it first, and a racing answer versus withdrawal has exactly one winner. Concurrent pickup has exactly one winner; a racing release versus substantive action either releases first (the former owner cannot then act) or the action commits first (release must obey the now-required reason). *Reason:* no lost evidence, double owner, or audit omission.
- **Approved [P15]:** Invalid inputs return a validation error; unauthorized writes return forbidden/not-found according to [P6]; invalid state, idempotency payload mismatch, or stale reviewed version return a conflict with a safe current-state indication when the actor may view the claim. A retry using the *same* successful idempotency key returns its original success rather than a state conflict. **If the current owner invokes `mark paid` again on that already-paid claim, return the original successful paid result** with the same paid-by and paid-at values; do not add activity, another payment confirmation, or any other side effect. A nonowner cannot use this replay behavior to obtain the result. *Reason:* a harmless repeat click is safe and observable as success without paying or logging twice.

### Kafka notification delivery (approved [P21–P24])

- **Agreed:** REST/PostgreSQL remain authoritative and available for claim work if the Kafka broker is down. Dashboard notices are asynchronous: claim detail, requests, decisions, queues, and exposure show committed changes immediately on the next REST read; the notice may appear later. The frontend reads notices from the backend over REST on refresh, not from Kafka or a WebSocket.
- **Approved [P21]:** A committed information request produces one notice for that claim's claimant; a committed answer produces one **team-scoped** notice on the claim's officer team's dashboard, including when no officer is assigned; a committed settlement or rejection produces one notice for the claimant. Capture destination ACCOUNT ID or immutable claim TEAM ID at action time, not when Kafka eventually processes the event. A same-team officer may see the answer notice even when someone else owns the claim, but only its owner can act. Events contain event/claim IDs, source version, type, destination and timestamp—not raw question/answer text, policy data, financial amounts, or internal reasoning. The notice links to an authorized claim read for details. No notice is generated for report, pickup, release, assessment, request withdrawal, or mark-paid in this scope. *Reason:* concrete, safe recipients without a third role or misleading owner routing after release.
- **Approved [P22]:** In the same PostgreSQL transaction as a successful notice-producing action, append history, its idempotency result, and one durable `notification_outbox` event. A background relay publishes undelivered events to a Kafka topic (for example, `claims.notifications.v1`) and retries with backoff on broker errors; no Kafka call is needed to commit the REST action. Kafka transport is **at least once**, not exactly once. Its consumer writes a dashboard notification using a unique event ID and marks the outbox row delivered **in one PostgreSQL transaction**, then acknowledges/commits the Kafka offset. If publish succeeded but the relay crashed, or database commit succeeded but offset commit failed, replay may deliver the event again; the unique ID yields one notice. Undelivered outbox events remain eligible for backoff-controlled republishing **without an attempt cutoff** even after a broker acknowledgment, so broker downtime or a prolonged consumer outage does not silently lose a committed notice to topic retention. Consumer failures remain retryable; operators can see outbox age/attempts and consumer errors rather than falsely treating broker acknowledgment as user-visible delivery. *Reason:* durable eventual notices without making Kafka availability a precondition for claim success.
- **Approved [P23]:** Run locally with the Spring Boot backend (including relay and consumer), PostgreSQL, one Kafka broker in single-node KRaft mode, and the same-origin frontend. Provide local orchestration/configuration for the broker and topic when implementation starts; no cloud account or external Kafka service. **The first full manual run starts with both PostgreSQL and Kafka running; no separate broker-down startup demo is required.** A healthy PostgreSQL is required for claim actions. If Kafka **goes down after startup**, REST claim actions must remain usable with committed outbox events pending; reconnect and deliver the notices after Kafka returns. Retain unconfirmed outbox events until delivery; local credentials/configuration must not be hard-coded as real production secrets. *Reason:* demonstrate normal local operation first without losing the broker-outage recovery guarantee.
- **Approved [P24]:** Expose paginated claimant and officer notification lists over authenticated REST, sorted by event occurrence time and stable event identity rather than assuming Kafka delivery order. Query by ACCOUNT destination for the claimant or TEAM destination for the logged-in officer; verify the linked claim remains visible on reads. No read/unread flag, dismiss action, streaming, or push is required. The notice list may lag while claim views remain current; the frontend shows notices after refresh and opens current claim/request/decision details through normal REST reads. *Reason:* observable broker-backed delivery without duplicating claim authority or leaking other teams' notices.

## 6. Exposure, workload, and read definitions

**Agreed exposure meanings:** Before a recorded estimate exists, unpaid exposure is **unknown**, never implicit zero. Requested amount, assessed loss, estimate, and settlement are not interchangeable. A settled-unpaid claim contributes its settlement amount as known exposure; a rejected or settled-paid claim contributes known zero. Never add different currencies into one numerical total.

- **Approved [P16]:** For `REPORTED`, `UNDER_REVIEW`, or `WAITING_FOR_CLAIMANT`, exposure is the most recently recorded nullable officer estimate, including explicitly known zero. A pre-decision estimate is the officer's current estimate of the insurer's *remaining unpaid* obligation, not a derived requested amount or `assessed_loss − requested_amount` figure; a missing requested amount does not change the rule that an unassessed claim has unknown exposure. Decisions supersede that estimate for reporting: settled-unpaid uses settlement amount, settled-paid/rejected use zero. Aggregate results group by currency, with `known_outstanding_total`, `unknown_claim_count`, and claim counts; a known total is labeled incomplete whenever unknown claims exist. Team filters apply before aggregation. These are estimates on reported claims, not full reserves, loss adjustment expenses, or IBNR. *Reason:* an honest number without fabricated certainty or exchange rates.
- **Approved [P17]:** Define a team's **open work** as undecided claims plus settled-but-unpaid claims; **resolved work** as rejected claims plus settled-and-paid claims. Also display **decided** count separately, including settled-unpaid. `time_to_decision` is decision timestamp minus report timestamp for claims decided within a chosen reporting period; show count and mean, with no mean when none qualify. Backlog counts are as-of the read, while decision-period counts use decision time, not incident time or payment time. No SLA, quality score, or cross-team/market organization view is implied. *Reason:* “open,” “resolved,” and “performance” otherwise conceal incompatible denominators.
- **Approved [P18]:** Officer list filters: `unassigned` includes all eligible team claims without an owner (including waiting-for-claimant and settled-unpaid); `mine` includes claims assigned to the caller; `waiting` includes team claims with OPEN claimant requests, with assignee shown; `team` includes all team claims including resolved read-only history. Rows include claim reference/type, market/currency, status, next actor, age since report, assignment, and permitted amount summary; use a stable default order and pagination. The team dashboard is restricted to the officer's team even when markets share a currency. *Reason:* find actionable work without exposing another team's claim details.

**Deliberate brief gap:** The brief's managers want a picture of outstanding claims and exposure. Team-scoped officer measures address **team** visibility only. With exactly two roles and no permission for officers to access other teams, this does **not** supply an organization-wide or six-market manager view. Do not label it one; broader authorized reporting requires a separate product/access decision, not an implicit officer privilege escalation. “Current on refresh” means querying committed data, not browser streaming.

## 7. Focused API contract (approved C1–C6)

**The following HTTP/JSON choices are approved, including C5's restricted claimant feed and C6's final fresh-clone requirement.** P1–P24 remain approved. In examples `<uuid>`, `<ref>`, `<instant>`, `<version>` and `<seed-password>` stand for values obtained from prior responses or local fixtures, not literal request text. Monetary amounts are decimal **strings** (e.g. `"2900.00"`) or JSON `null`; incident dates use `YYYY-MM-DD`, timestamps use UTC ISO-8601. The backend derives claimant, team, market and currency; clients cannot assign them. Examples show complete request bodies (except optional fields explicitly noted). All reads and results are filtered for the authenticated actor.

- **Approved [C1] (session and CSRF):** Cookie-based same-origin sessions. Anonymous `GET /api/csrf` returns `200 {"csrfToken":"<token>"}` and a session cookie. `POST /api/session` with header `X-CSRF-Token: <token>` and body `{"email":"a@local.test","password":"<seed-password>"}` returns `200 {"account":{"id":"<uuid>","email":"a@local.test","role":"CLAIMANT","market":{"code":"SG","currency":"SGD"}},"csrfToken":"<new-token>"}` and a session cookie. For an officer, `role` is `OFFICER` and `teamId` replaces `market`. Authenticated `GET /api/session` returns that account and the current token; `DELETE /api/session` with CSRF token returns `204`. Subsequent writes send the current CSRF token and cookie. Wrong credentials: `401 BAD_CREDENTIALS`; no login: `401 AUTH_REQUIRED`; missing/invalid CSRF: `403 CSRF_INVALID`. *Reason:* test real browser auth without turning off CSRF.
- **Approved [C2] (role-scoped shapes):** Claim detail and claim mutations return `{"claim":ClaimView}`; request creation, answer and withdrawal return `{"request":RequestView,"claim":ClaimView}`. Claimant `ClaimView` has `id`, `reference`, `reportedAt`, `market`, `currency`, `type`, `incident` (with `date`, `location`, `description`, `affectedAsset`), nullable `policyReference`, nullable `requestedAmount`, `status`, `nextActor`, nullable `decision`, nullable `payment`, `informationRequests` (array of RequestView), and numeric `version`. Immediately after reporting: `status:"REPORTED"`, `nextActor:"OFFICER"`, both decision/payment null, empty requests, `version:1`. Officer `ClaimView` additionally has `teamId`, nullable `assignedOfficerId`, `assessment` (keys `coverage`, nullable `reason`, nullable `assessedLoss`, nullable `estimatedUnpaidAmount`; coverage is `UNKNOWN`, `APPEARS_COVERED`, or `APPEARS_NOT_COVERED`) and `exposure:{"known":boolean,"amount":null|string}`. The claimant projection **omits** those officer-only fields. RequestView has `id`, `claimId`, `question`, `status` (`OPEN`, `ANSWERED`, or `WITHDRAWN`), nullable `answer`, `requestedAt`, nullable `answeredAt`; withdrawal reason appears only in officer activity. Decision has `kind` (`SETTLED` or `REJECTED`), nullable `amount`, `reason`, and `decidedAt`. Payment is null until settlement, then has `status` (`UNPAID` or `PAID`) and nullable `confirmedAt`; officer projection adds nullable `confirmedByOfficerId`. `nextActor` is `CLAIMANT`, `OFFICER`, or `NONE` per §4. Decimal strings follow the configured ISO currency's scale (SGD examples use two fractional digits), not a hard-coded SGD rule. *Reason:* role-safe progress without leaking assessments or officer notes.
- **Approved [C3] (idempotency/version):** Report, request creation, answer and decision require header `Idempotency-Key: <unique-client-key>`. Same actor/key/identical body replays the **original HTTP status, Location header (if any), and body** even when the claim later advances; changed body with that key gives `409 IDEMPOTENCY_CONFLICT`. The decision JSON includes numeric `reviewedVersion` from the last officer claim read; a stale value gives `409 STALE_VERSION` with current version for an authorized viewer. `POST /mark-paid` needs no key; the same current owner repeats it for the identical original `200` body with no write. *Reason:* clear lost-response and evidence-race behavior.
- **Approved [C4] (errors):** Non-2xx JSON is `{"error":{"code":"CODE","message":"Safe explanation"}}`; only a visible `STALE_VERSION` adds `"currentVersion":<number>` inside `error`. Malformed/invalid fields or disallowed market: `400 INVALID_INPUT`; missing idempotency key: `400 IDEMPOTENCY_KEY_REQUIRED`; required release reason missing/blank: `400 REASON_REQUIRED`. Unauthenticated: `401 AUTH_REQUIRED`; wrong role or visible nonowner mutation: `403 FORBIDDEN`; nonexistent or hidden claim/request: `404 NOT_FOUND`. Invalid lifecycle or closed request: `409 STATE_CONFLICT`; losing atomic pickup: `409 ALREADY_ASSIGNED`; decision while information request OPEN: `409 OPEN_REQUEST`; settlement lacking recorded covered assessment/reason/assessed loss: `409 MISSING_ASSESSMENT`; key reuse with different body: `409 IDEMPOTENCY_CONFLICT`; stale decision: `409 STALE_VERSION`. Authorization runs before returning version or state details. *Reason:* clients can tell correction from a race without leaking another user's claim.
- **Approved [C5] (lists/summary/notices):** `GET /api/claims`, `GET /api/officer/claims?view=unassigned|mine|waiting|team`, `GET /api/claims/{id}/activity`, and `GET /api/notifications` return `{"items":[...],"nextCursor":null|"<opaque>"}`. Optional `limit` defaults to 20 (maximum 100), with optional `cursor`; newest-first ordering is stable. Claim list items contain `id`, `reference`, `market`, `currency`, `type`, `status`, `nextActor`, `version`; officer rows add `assignedOfficerId` and `teamId`. **Officer-only** activity items contain `type`, `actorId`, `occurredAt`, `details`, including release `details.reason`. **Claimant** activity items instead contain **only** `type`, `occurredAt`, and a server-authored generic `message`. Allowed claimant types are `CLAIM_REPORTED`, `INFORMATION_REQUESTED`, `INFORMATION_RECEIVED`, `REQUEST_WITHDRAWN`, `DECISION_AVAILABLE`, and `PAYMENT_CONFIRMED`; do **not** include pickup, assignment, release, assessment or any other internal officer actions. Claimant items never contain actor IDs, `details`, release/withdrawal reasons, raw request/answer text, assessment, reserves or other internal data. Claimant messages are fixed safe progress text; specific request wording and final decision/reason are obtained through the authorized claim detail, not copied into the feed. Notice items contain only `id` (event ID), `type` (`REQUESTED`, `ANSWERED`, or `DECIDED`), `claimId`, `claimReference`, `occurredAt`, not question/answer/money. `GET /api/officer/team/summary?from=<instant>&to=<instant>` takes an inclusive start/exclusive end for decision metrics; an empty-team response is `{"teamId":"<uuid>","openCount":0,"decidedCount":0,"resolvedCount":0,"decisionCount":0,"meanTimeToDecisionSeconds":null,"exposureByCurrency":[]}`. Each currency row has `currency`, `knownOutstandingTotal` (decimal string), `unknownClaimCount`, `claimCount`, and `incomplete` (boolean); e.g. one unassessed SG claim gives `{"currency":"SGD","knownOutstandingTotal":"0.00","unknownClaimCount":1,"claimCount":1,"incomplete":true}`. Rows exist only for currencies **present among team claims**. First three counts and exposure are current inventory; decisionCount and the mean (integer seconds rounded to nearest second, null when no decisions) use only decisions in `[from,to)`. *Reason:* a role-specific progress projection rather than a redacted copy of internal officer history.
- **Approved [C6] (fixtures, fault setup and fresh clone):** Use pre-created A/B (SG claimants) and O1/O2 (the seeded SG team); fixture-only O3 belongs to a different team and fixture-only M2 is a market with a different ISO currency (optionally routed to O1's team). Supply test passwords outside version control. Assertions use **HTTP only** for state and notices; Compose may stop/restart Kafka to trigger an outage, and a broker fixture may redeliver a previously delivered event ID. Neither setup counts as testing internal Java classes or database tables. **Final fresh-clone acceptance requires `./start.sh` to start the Java app, PostgreSQL and Kafka (including the topic), and wait for all three to be ready, in one command, with Docker running but without any pre-existing `.env`, local database or host-installed Java, Python or OpenSSL.** An ignored local secret may be created automatically without committing credentials; the Java build/runtime and any credential-generation utilities must be provided by the local Docker-backed setup, not required on the host. *Reason:* the submitted application must work on a clean machine, not merely demonstrate infrastructure readiness.

### Operation contract (approved C1–C5)

Each POST/PUT/DELETE uses C1's session and CSRF header. `{}` is a complete empty request body; no body is implied for GET. C3's Idempotency-Key is required only where shown. On successful creation, `201` includes the stated `Location`; a replay preserves that original header. Other writes return `200` with the C2 role projection of the committed result. A duplicate mark-paid by its current owner performs **no** second commit.

## 8. Focused API-level acceptance plan (not test code)

Use isolated claims/fixtures per scenario so summary counts are reproducible. Docker/Kafka manipulation in S8 is fault setup only; assertions remain API-level. All writes use the actor's cookie and current CSRF token.

## 10. Approved decisions and API-contract boundary

**All P1–P24 rules are approved as written here, including the revisions to P2, P11, P15 and P23.** This table highlights consequences; it does not reopen these decisions.

| Approved decision | Confirmed behavior | Tradeoff |
| --- | --- | --- |
| **Routing [P2]** | Seed **only SG/SGD** and **one team for both MOTOR and PROPERTY**. Derive market/currency/team from configurable data; a claimant reports only in their account's market. A second currency is introduced through a later fixture, never hard-coded into claim logic. | A small local seed does not pretend to implement all six markets; configurable routing remains testable. |
| **Filling missing data [P3, P20]** | Optional reference/amount at report; request and text answer on the existing claim, with optional structured fields to fill/correct either value. No automatic parsing or amount-to-exposure conversion. | First report stays easy; structured answers and versioned history require care. |
| **Settlement prerequisites [P4, P10, P11]** | Require recorded **assessed loss**, `APPEARS_COVERED` with reason, positive settlement amount/explanation, and no open information request. Rejection requires reason but **not** assessed loss or a negative coverage conclusion. | The officer must explain an assessed settlement without pretending the typed policy reference was verified. |
| **Settled-unpaid handover and repeat payment [P9, P12, P15]** | Allow reasoned release, same-team pickup and one payment confirmation. A second mark-paid by the same owner returns the original success/actor/time without a second entry. Never re-decide. | Payment tasks can be handed over without turning a repeated click into another payment event. |
| **Resolved versus decided [P17]** | Settled-unpaid is **decided but open work**; rejected/settled-paid is **resolved**. Time to decision is from report to decision. | “Resolved” is an explicit product measure, not a universal insurance KPI. |
| **Outstanding request versus final decision [P10, P14]** | Block decision while a request is open; allow reasoned withdrawal, serialize withdrawal and answer, and reject decisions based on a stale reviewed version. | Prevents disregarding claimant evidence; adds an explicit step and possible conflict/review retry. |
| **Who gets dashboard notices [P21, P24]** | Request and decision → claimant; answer → claim's officer team, including unassigned cases. Show safe role-filtered notices via REST after Kafka delivery. | A team notice may be seen by several authorized officers and may lag the authoritative claim view. |
| **Local Kafka and delivery [P13, P22, P23]** | First full manual run starts with **PostgreSQL and Kafka running**. If Kafka later fails, commit claims and outbox normally and catch up after recovery; idempotency keys and unique event IDs prevent duplicate notices. | Durable asynchronous delivery adds a broker and monitoring, but does not block claim work on a later broker outage. |
